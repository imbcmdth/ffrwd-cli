# ffrwd

A compiler from Postgres-dialect SQL to ffmpeg commands. A query names
the streams it wants and where they go; ffrwd probes the inputs,
resolves the graph, and prints the command. It is published on PyPI, so
the repo's `../README.md` is a storefront and a breaking change reaches
real users.

## The pipeline

    parse -> resolve -> probe -> lower -> insert_splits -> emit

`parser.py` reads Postgres through sqlglot. `probe.py` runs ffprobe once
per distinct path. `lower.py` is the bulk of the work, SQL to IR.
`split.py` inserts a `split` wherever a stream has more than one
consumer. `emit.py` renders argv. `registry.py` introspects the local
ffmpeg for its filters and their options; `tests/data/reference_registry.json`
pins a known build so tests do not drift with whatever is installed.

Everything is **compile-time countable**: every relation's size is known
before ffmpeg runs. That is what lets `WHERE` filter tracks at compile
time, and what keeps the one-row rule decidable.

`ARCHITECTURE.md` beside this file says what each stage may know and
decide, the invariants a change preserves, how to compose one so a fact
has one home, and the failures each rule was paid for with. Read it
before changing the compiler.

## Layout

- `ffrwd/` — the compiler. `functions.py` expands user-defined
  functions at each call site; `project.py`, `store.py` and
  `packages.py` are the package system; `cli.py` is the surface.
- `../docs/` — at the repo root, shared. `examples.md` is both the
  cookbook and a test corpus.
- `tests/` — the unit tier by default; the `exec` tier runs real ffmpeg.
- The registry is a separate repo, `../../sqlmpeg-registry`, publishing
  to ffrwd.video.

## Branches

`main` is the shipped thing and stays clean. `dev-tools` carries
`plans/`, `ROADMAP.md` and `scripts/hunt.py` — working notes that should
not ship. Plans are written and read there.

Merges must be fast-forward. `--no-ff` fails in this environment.

## How work happens

Numbered plans in `plans/` on `dev-tools`, dispatched to subagents one
wave at a time.

- **Agents do not commit.** Work is left uncommitted and reviewed first.
- Prose — plans, docs, reports — is written by the reviewer, never
  delegated.

## Guardrails

- **Never push anything failing locally.** ruff, `mypy --strict` and the
  unit tier are green before anything leaves the machine.
- **Recipes before implementation.** A feature starts as an entry in
  `../docs/examples.md`, red, and goes green when it lands. No xfail
  tiers.
- **Never hand-type an ffmpeg command line.** Every pinned command in
  the cookbook is generated by running the compiler. A hand-written pin
  tests the typist.
- **Derive expectations from descriptions, never from output.** When a
  test fails, the fixture is not the thing to change until you know why
  it failed.
- The words **"fence"** and **"gate"** appear nowhere — not in code,
  comments, docs or reports.
- **Never cite a plan or RFC number** in code, comments, docstrings or
  error messages. They mean nothing to a reader six months from now.
- Comments say WHAT, briefly. Why and how only where the code cannot.
- `../README.md` is prose for a newcomer. `../docs/*.md` is terse
  reference — what, how, when, and no backstory.
- Use ordinary terminology. Do not invent names for things.
- Errors are typed, line-anchored, and carry a hint. That contract is
  what `../docs/error-schema.json` pins and what the MCP repair loop
  reads.
- `-o` is unadvertised and may be removed. Prefer `COPY ... TO` with
  `-v`.

## Tests

Budgeted by runtime, because a suite nobody waits for is a suite nobody
runs.

- unit — seconds to a few minutes
- exec, running real ffmpeg — single-digit minutes
- anything longer runs nightly, and only if nothing waits on it

When a tier gets slow, cut its shape rather than accept the time. One
representative fixture — a file with several video and audio tracks,
plus a negative case — beats a matrix of hand-tuned ones.

A unit test never reads `tests/fixtures/` and never invokes ffmpeg —
CI's unit step runs on a bare machine with neither, so such a test is
green locally and red in CI. Real files and real ffmpeg are the exec
tier's, by definition; a lowering property wants a synthetic
`ProbeResult`, and a subscripted stream lowers symbolically against a
path that does not even exist.

A test earns its place by a new path or a new assertion: a test whose
execution path an existing test already walks must assert something
that test does not, or join it. Static tables get ONE table-equality
test, not a case per row; a pass's field-preservation invariants get
one structural test over a fully-populated graph, not a test per
field. The exception that stays parameterized: refusal sweeps where
each case pins a distinct message — those assert unique behavior on
shared lines. The count of tests is not the measure of the suite;
what a failure would catch is.

## Releasing

Never publish by hand.

The cli and the sidecar wheel are version-locked: one number, one tag,
both published together even when only one changed — "cli at X.Y uses
sidecar at X.Y" is always true.

1. Full local checks green.
2. Push the feature commits; wait for CI.
3. Bump ALL FOUR version sites to the same X.Y.Z: `uv version X.Y.Z`
   here (it does not tag), the three marker-gated
   `ffrwd-wasm==X.Y.Z` pins in dependencies, `../sidecar/Cargo.toml`'s workspace version, and
   `../sidecar/ffrwd-wasm/pyproject.toml`. Commit the bump. The release
   workflow refuses a tag whose versions disagree.
4. Annotated tag `vX.Y.Z` on the bump commit.
5. Push the commit and the tag together — the one tag releases both
   packages.

Commits are SSH-signed, and `main` requires verified signatures.
